huawei_c_model 架構與微架構文件

本文件說明 huawei_c_model 的軟體與微架構設計。這是一個 C++ cycle-accurate、bufferless、deflection-routed 的多環（multi-ring）NoC 模擬器，主要用於模擬類似 Huawei CMN 的 chiplet 互連網路架構。

Ring (環)
CrossStation (站點)
RBRG_L1 (Die內橋接)
RBRG_L2 (Die對Die橋接)
SwapSink (SWAP恢復)

1. 高層架構

模擬器的架構由下往上呈現層次結構：最底層為 Ring，每個 Ring 包含多個 CrossStation，不同的環之間透過橋接器相連。RBRG_L1 用於 die 內的 ring 橋接，而 RBRG_L2 則用於 die 對 die (D2D) 的橋接，並且 RBRG_L2 同時實作了 SwapSink 介面以支援死結恢復。

拓樸結構由 YAML 設定檔定義，實際包含幾種不同的組態：

  • server_cpu (configs/server_cpu.yaml)：包含兩個環（CCD0 和 IOD0）。只有 CCD0 的 type: full（雙向環），而 IOD0 為 type: half（單向順時針 CW 環）。這兩個環透過一個 RBRG_L2 橋接相連。
  • ai_processor (configs/ai_processor.yaml, configs/ca_verify_3x3.yaml)：建立垂直與水平交錯的網格狀環路。所有的環均為 type: half（單向 CW）。在網格的每個交會點，透過多個 RBRG_L1 進行連線，不包含 RBRG_L2。

2. 微架構 / 週期模型

所有模擬元件繼承自基礎類別 Component（include/component.hpp），並實作 tick() 與 tock() 兩階段的週期模型。這種設計的目的是為了避免同一週期內的 read-after-write 危害（Race conditions）。在 tick() 階段中，元件僅讀取 curr_*（當前狀態）並運算決策後寫入 next_*；在 tock() 階段才統一將 next_* 提交為 curr_*。

元件的執行順序由其被插入 Simulator::components 的順序嚴格決定。在 Simulator::build_from_config() 的建構過程中，所有的 CrossStation 都會先於橋接器被加入。這確保了每個 CrossStation::tick() 一定會在同一週期內的任何 bridge 的 tick() 之前執行完畢。因此，RBRG_L1 和 RBRG_L2 在 tick() 階段可以直接讀取 Ring 上的 next_cw_slots 作為「這個週期已經被站點決定好的輸出」。

值得注意的是，Ring::tick() 本身是空的。修改 Ring slot 內容的實際工作是在 CrossStation::tick() 寫入，而 Ring::tock() 才執行真正的 slot 旋轉移動邏輯。

3. Ring Slot 機制

Ring 使用雙緩衝陣列 curr_cw_slots 與 next_cw_slots 來管理環上的狀態（如果是雙向環，還會有一組 ccw 版本），每個元素是一個 RingSlot（include/ring_slot.hpp）。在每週期的 Ring::tock() 中，系統會執行旋轉邏輯，將所有 slot 往同方向前進一格。

在方向選擇上，雖然 CrossStation::choose_direction() 實作了根據 CW/CCW 最短距離選擇方向的邏輯，但實際上在流量產生路徑中從未被呼叫。HotspotGenerator 產生的所有流量都被硬編碼為順時針（CW）方向。因此，最短路徑方向選擇在架構程式碼中存在，但目前的實驗皆未使用，只有單元測試會覆蓋這段邏輯。

4. Deflection Routing + I-tag / E-tag

在 CrossStation::process_direction() 中，當 flit 抵達目的地站點時，會嘗試進行本地 ejection。它會檢查 dst_node 是否相符，並嘗試放入 EjectQueue。如果 ejection 失敗（佇列滿載），則發生 deflection（deflect_count++）。

E-tag (Ejection Reservation): 當發生 deflection 時，如果 EjectQueue 允許預留，該站點會在 outgoing slot 上蓋上 E-tag（設定 e_tag = true、e_tag_owner_station、e_tag_flit_id）。當這個 flit 繞環一圈回來時，如果 E-tag 還在，它將保證能被 eject。如果是別的 flit 帶著 E-tag 抵達，預留會靜默失效。同理，I-tag (Injection Reservation) 提供注入預留機制以防止飢餓。

EjectQueue 容量與預留語意 (include/node_interface.hpp): can_reserve() 函數只檢查當前預留數量是否小於 max_reservations，與實體容量無關；這代表即使實體佇列全滿也能核准 E-tag 預留。相反地，一般無預留的 has_space() 檢查會同時將實體數量與預留數量合併計算。當 flit 真正呼叫 push() 進入佇列時，只有在當下真的有實體空間時，才會把 flit 放進去並消耗掉對應的預留；如果物理上滿載，它不會吃掉這個預留，而是讓 flit 繼續 deflect 留待下次。

5. RBRG_L1（Die 內橋接）

在 AI-processor 的網格拓樸中，垂直與水平環交會處透過 RBRG_L1 橋接（建構時依據環大小與交會邏輯計算配置）。其內部結構包含一個長度為 latency_cycles 的 pipeline (pipeline_regs_curr/next) 以及 ingress_queue 與 egress_queue。

在 tick() 的執行順序中，RBRG_L1 會從本地環的 next_*_slots 偷取（Steal） 封包進入 ingress queue，前提是 queue 未滿（受限於 queue_depth）且路由檢查（should_forward_to_ring）允許。封包接著進入 pipeline 延遲，最後進入 egress queue 準備注入對面的環。注入時優先嘗試 CW，若被佔用且為雙向環才 fallback 到 CCW。此處沒有實作 egress 端的最短路徑方向選擇（原始碼內有註解說明這是簡化）。

6. RBRG_L2（Die 對 Die 橋接）

RBRG_L2 僅在 server_cpu 風格的設定中建立，實體化自 YAML 內的 bridges: 條目。值得注意的是，其 queue_depth 與 initial_credits 在 build_from_config() 的呼叫端被寫死為 4 和 16，無法透過 YAML 設定（僅 d2d_latency_cycles 可設定）。

它與 L1 的關鍵差異在於反壓（Backpressure）機制與 SWAP 實作。RBRG_L1 佇列滿了只會讓上游發生 deflection，而 L2 實作了 Credit-based 反壓模型。它包含兩組平行的 pipeline：一組 d2d_pipeline 傳輸 flit，另一組方向相反的 credit_pipeline 模擬對等的 credit 回傳延遲。注入 pipeline 前會檢查 current_credits。此外，L2 實作了 SwapSink 介面，其 reserved_tx_buffer 用來接收因死結恢復而被驅逐的受害封包，且在注入空的 pipeline slot 時，此 buffer 的優先級高於一般的 local_rx_queue。

7. SWAP 死結恢復

死結恢復機制（DRM）在 CrossStation 內實作為一個簡化過的二態布林開關（drm_active），而非複雜的多狀態機。當 consecutive_inject_fail_cycles 超過 deadlock_threshold_cycles 時開啟。因為是簡化版，只要有任何一次本地注入成功，drm_active 就會立刻被關閉，沒有複雜的退避延滯機制。

觸發 SWAP 的條件包含：drm_active 為真、本地有一個滿載的 eject queue、一個等待注入的封包，以及必須接有一個 SwapSink。在同一個 tick() 內會發生原子性的三方交換：

  1. 將 eject queue 裡最舊的封包驅逐至 SwapSink（RBRG_L2）。
  2. 將佔據 ring slot、正在繞環中的封包強制 eject 進入剛空出來的位置。
  3. 將本地等待中的封包直接注入至 ring slot 上。

SWAP 的拓樸限制

目前只有 RBRG_L2 實作了 SwapSink 介面。這意味著在完全沒有 RBRG_L2 的 AI-processor 網格拓樸中，即使 drm_active 被觸發，由於 swap_sink == nullptr，SWAP 的恢復邏輯完全不會執行，變為無效的靜默操作。

8. Simulator 調度

系統啟動時，會經過 Config::parse() 將 YAML 對應至各個 C++ 結構（RingConfig、RBRGL1Config 等）。這是一個 fail-fast 流程，若缺少必要欄位會拋出異常。隨後 build_from_config() 會產生物件圖並註冊到 components 清單中（init_topology() 等是僅限單元測試使用的舊代碼）。

雖然 Simulator::run() 存在，但在正式實驗的路徑（main.cpp）中並沒有被呼叫。實際運作的是兩個手動寫出的迴圈：

  • run_server_experiment()：掃描注入率，HotspotGenerator 目標為 DDRC。迴圈內會呼叫 tick/tock 並手動排空 eject queue，輸出至 server_latency.csv。
  • run_ai_experiment()：名為「read/write ratio」掃描，但流量產生器裡實際上沒有 FlitType 的區分邏輯，本質上依舊是注入率掃描，輸出至 ai_bandwidth.csv。
  • run_ca_verify()：在 3x3 組態上手動注入封包，跳過流量產生器，用以匯出 Cycle-Accurate 視覺化的 JSON trace。

9. 統計與追蹤

StatCollector（在 stats.cpp 內）目前只是一個空殼，tick() 為空操作，tock() 僅累加週期數。報告的各項指標實際上都是在 main.cpp 的實驗迴圈裡手動累加算出的。

Latency 的計算陷阱： Flit 結構內的 create_cycle 與 inject_cycle 宣告了但從未被賦值。目前的實作中，eject_cycle 被挪用來儲存 hop_count。因此，main.cpp 計算輸出的 "average_latency" 實際上是平均跳數（Hop count）。因為 deflection 發生在目的地時不會增加 hop_count，這個數值會略微低估封包在網路中經歷的真實週期數。

至於視覺化的 Trace JSON，TraceDumper 負責錄製各週期的 buffer 狀態。但需要注意：它只支援追蹤 RBRG_L1；對於 RBRG_L2 與 Die 對 Die 拓樸完全沒有提供視覺化的支援。

11. 文件/計畫與目前實作之間的落差

⚠️ 實作落差 (Implementation Gaps)

下列為原始 Huawei_CA_model_plan.md 設計文件與當前程式碼庫的實際差異。接手與維護者請務必以此為準，避免錯誤假設：

  • StatCollector 是空殼：計畫中的延遲百分位、bridge 佔用率皆無實作；出貨實驗指標全在 main.cpp 中臨時湊算。
  • 時間戳欄位為假：Flit::create_cycle/inject_cycle 皆為死欄位未賦值；eject_cycle 實質上存的是 hop_count，計算出的不是真實的 cycle 延遲。
  • 方向選擇形同虛設：CW/CCW 最短路徑選擇邏輯雖存在，但 HotspotGenerator 硬編碼為 CW，實際實驗中未被觸發。
  • DRM 並非狀態機：DRM 實作為一簡單布林開關，無退避延滯機制，只要注入成功一次即退出。
  • SWAP 在 AI 拓樸無效：由於 SWAP 需要 SwapSink（目前只有 RBRG_L2 實作），在 AI-processor 中即使觸發 DRM 也是靜默無效的操作。
  • RBRG_L2 參數寫死：其 queue_depth 與 credit_depth 在程式碼中寫死，無法透過 YAML 配置。
  • Trace 視覺化限制：完全不支援 RBRG_L2 或是 Die 對 Die 的拓樸，僅捕捉 L1 Bridge。
  • AI 實驗的「讀寫比」假象：雖然實驗名稱宣稱測試讀寫比（read/write ratio），但流量產生器無區分 flit type 邏輯，純粹只是重新命名後的注入率掃描。
  • 執行入口殘留：Simulator::run() 與 init_topology() 等函數目前皆為測試用殘留代碼，正式實驗手寫了自己的迴圈。
  • 物理參數缺失：設計計畫中的頻率、站點間距等物理建模參數，在 Config 中完全沒有對應的實作欄位。
